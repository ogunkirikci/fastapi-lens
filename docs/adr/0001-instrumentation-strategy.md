# ADR 0001: FastAPI Instrumentation Strategy

- Status: Accepted for implementation
- Date: 2026-08-02
- Decision owners: fastapi-lens maintainers

## Context

`fastapi-lens` needs execution boundaries that FastAPI does not expose through a
stable public profiler API. The first release must measure:

- ASGI response lifecycle checkpoints
- Endpoint handler wall time
- Dependency setup, cleanup, caching, and nesting
- Response serialization
- SQLAlchemy query execution

Instrumentation must preserve application behavior, dependency overrides,
cache identity, generator exception semantics, teardown order, and concurrent
request isolation.

The feasibility spike lives under `tests/spike/`. It is disposable research
code and is not imported by the production package.

## Versions examined

The spike executed against the development environment:

| Component | Version |
|---|---|
| Python | 3.11.15 |
| FastAPI | 0.141.1 |
| Starlette | 1.3.1 |
| SQLAlchemy | 2.0.51 |

Capability and signature checks also ran against FastAPI:

- 0.121.0
- 0.128.0
- 0.139.2
- 0.141.1

All sampled releases expose dependency scopes, `run_endpoint_function`,
`serialize_response`, and separate request/function exit stacks. Internal
function signatures changed across the sampled releases:

- `serialize_response` gained `endpoint_ctx`.
- `serialize_response` later gained `dump_json`.
- `solve_dependencies` expanded accepted body types.
- `solve_dependencies` later gained `_uses_scopes_cache`.

These are internal APIs. Capability detection and versioned adapters remain
mandatory even when a function name exists across all sampled releases.

## Decision

### 1. Lifecycle collection uses pure ASGI middleware

The collector records:

- Request receipt
- Response start
- Completion of the final response body send
- Downstream application completion

The final body checkpoint is recorded after the wrapped `send` await returns.
This captures server-side backpressure but does not claim that bytes reached the
remote client.

The production middleware must not inherit from `BaseHTTPMiddleware`.

#### Middleware placement limitation

When Lens wraps the complete FastAPI ASGI application, it observes the 500
response generated by FastAPI's outer error middleware and also observes the
re-raised exception.

Middleware installed with `app.add_middleware` sits inside FastAPI's outer error
middleware. It sees the exception but cannot observe the outer 500 response.

`Lens(app)` cannot replace the caller's application reference. The first
implementation will therefore:

- Capture normal response checkpoints through app middleware.
- Finalize unhandled exceptions as incomplete when the outer 500 is not visible.
- Record the exception without changing propagation.
- Document that complete outer-error response timing requires explicit ASGI
  wrapping in a future optional integration form.

### 2. Handler timing uses `run_endpoint_function`

FastAPI exposes a dedicated internal `run_endpoint_function` boundary in every
sampled release. A versioned, reference-counted process registry will wrap this
function.

The handler segment reports wall-clock time. For sync handlers this includes
thread-pool scheduling. v0.1 does not claim to separate queue wait from callable
execution.

Generator endpoints follow separate FastAPI streaming branches and do not pass
through this hook. They use lifecycle timing and are labeled accordingly.

### 3. Serialization timing uses `serialize_response`

A versioned wrapper around `fastapi.routing.serialize_response` records one
combined serialization segment. The wrapper forwards keyword arguments without
reconstructing them.

Custom `Response` instances and streaming responses legitimately bypass this
hook. Their serialization state is not applicable rather than zero-duration.

Adapter capability metadata records whether `endpoint_ctx` and `dump_json` are
present. The wrapper must not inject unsupported arguments.

### 4. Per-dependency timing uses a versioned solver adapter

There is no stable hook around each dependency invocation. The selected design
is a versioned adapter derived from the supported FastAPI
`solve_dependencies` implementation.

The adapter will instrument the exact branch where FastAPI:

- Returns a cached value
- Enters a sync or async generator
- Awaits an async callable
- Runs a sync callable in the thread pool

The adapter preserves the original `Dependant.call` object and cache key.

For generator dependencies, it delegates through the original context manager
and records:

- Setup around context entry
- Cleanup around context exit

This preserves exception injection and LIFO exit-stack behavior.

The adapter must replace both references used by FastAPI:

- `fastapi.dependencies.utils.solve_dependencies`
- The imported `solve_dependencies` reference in `fastapi.routing`

Installation and restoration are process-global, thread-safe,
reference-counted, and safe with multiple Lens instances.

#### Rejected: mutating `Dependant.call`

The route-tree wrapper prototype can preserve cache behavior only when every
reference to the same original callable shares one wrapper object.

It is rejected because:

- A late `app.dependency_overrides[original]` lookup no longer matches the
  wrapped callable.
- Generator wrappers must reproduce exception injection and teardown semantics.
- Callable mutation affects other tooling that inspects the dependency graph.
- Restore behavior becomes fragile when routes or overrides change at runtime.

The spike includes a regression test that demonstrates the broken override.

#### Rejected: wrapping only `solve_dependencies`

Measuring one recursive `solve_dependencies` call does not measure the
dependency represented by that call. FastAPI invokes that dependency in the
parent recursion frame after sub-dependencies resolve. A shallow wrapper would
therefore report misleading boundaries.

### 5. Request context uses `ContextVar`

AnyIO propagates request context into sync dependency worker threads in the
sampled environment. The production collector will still test this across the
supported matrix.

Segment stacks use immutable tuples so parallel child tasks receive independent
stack snapshots. The mutable collector applies its own synchronization for
thread-pool writes.

### 6. SQLAlchemy uses explicit engine listeners

Users register engines explicitly. For `AsyncEngine`, listeners target
`engine.sync_engine`.

The selected events are:

- `before_cursor_execute`
- `after_cursor_execute`
- `handle_error`

Timing stacks live in `Connection.info` under a probe-specific key. Request
association uses `ContextVar`. Bind values are not stored. Pre-ping errors are
excluded with `ExceptionContext.is_pre_ping`.

Registration is idempotent and reference-counted. Removing one owner does not
remove listeners still used by another owner.

The spike proves sync queries, async queries, failed queries, and final listener
removal without changing SQLAlchemy exceptions.

## Compatibility policy

The initial development range is:

```text
FastAPI >=0.121.0,<0.142.0
```

This range became the initial release claim after the capability probes and
adapter suites passed. Every supported version must continue to meet these
conditions:

- Its capability probe must pass.
- Its adapter test suite must pass.
- Dependency cache, overrides, scopes, exceptions, and teardown tests must pass.
- Handler and serialization boundary tests must pass.

Adapters fail fast on an unknown signature or source-behavior guard. They never
silently fall back to partial dependency instrumentation.

The first implementation should organize adapter families by observed
capabilities rather than one large conditional function. New FastAPI minors are
unsupported until CI confirms an existing adapter or adds a new one.

## Multi-application lifecycle

Process-global patches use an ownership registry:

1. The first Lens owner installs the wrapper.
2. Additional owners increment ownership without wrapping again.
3. Removing one owner leaves instrumentation active.
4. Removing the final owner restores the exact original callable.

The spike proves this lifecycle with two FastAPI applications.

## Consequences

### Positive

- Lifecycle timing follows ASGI events rather than response-object creation.
- Dependency cache and override identity remain intact.
- Setup and cleanup have truthful boundaries.
- Multiple applications can share process-global hooks.
- SQLAlchemy sync and async engines use the same event model.

### Negative

- Dependency instrumentation requires maintenance for FastAPI internals.
- FastAPI version support must be explicit and tested.
- `Lens(app)` cannot observe the outer generated 500 response through normal
  middleware registration.
- Global handler and serialization wrappers require careful restoration.

## Go or no-go decision

**Go**, with the following gates:

- Implement dependency instrumentation only through versioned solver adapters.
- Keep all FastAPI internal integration in one adapter package.
- Fail fast for unsupported adapter capabilities.
- Keep pure ASGI lifecycle collection independent of the FastAPI adapter.
- Do not promote spike code directly into production modules.

TASK-002 may begin using the lifecycle and segment semantics established by
this ADR.
